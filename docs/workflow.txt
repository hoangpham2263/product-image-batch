WORKFLOW AND PROJECT STRUCTURE

Entry points
  start-app.cmd -> src/gui.ps1 -> src/ui/main-window.ps1
  run.cmd -> src/run-images.ps1 -> bootstrap.ps1 -> Invoke-BatchWorkflow
  Existing command-line parameters and shortcuts remain compatible.

Batch preparation
  The entry point validates arguments and resolves paths.
  application/configuration.ps1 loads product contexts, catalog and writing rules.
  bootstrap.ps1 defines the same ordered module list for main process and workers.
  BatchWorkflow locks urls.txt, reads valid URLs, creates batch folders and starts
  a bounded runspace pool. Each URL has its own item ID and files.
  Each worker receives an independent configuration snapshot. A per-item error log
  preserves the full diagnostic stack while the GUI shows only the main failure.

Per-product steps, in execution order
  01 LoadProduct
     Input: URL and product handle.
     Output: local product reference and an image-based product classification.
     Familiar apparel can reuse editorial contexts. Unknown categories are derived
     dynamically from the actual product, not from a fixed industry list.
     Presentation can be worn, held, placed or vehicle; these control composition.
     Missing/unusable product references stop this item.

  02 SelectReferences
     Input: reference, context and requested reference count.
     Output: one subject reference plus compatible scene references if available.
     Category takes priority, then original/stock provenance, then mixed review
     photos. Library candidates require a suitability check; user-attached photos are used directly after file/hash checks.
     Scene checks include the actual product and the selected person when relevant.
     Candidates come from data/source-photos/ via catalog.json categories.
     A real reference is required. If none passes the check, the item
     stops, its URL remains queued and missing-data/<item>/ records the product
     image and info.json. The batch writes missing-data.csv after all workers finish.
     Object scenes do not require people, clothing, fictional names or a golf example.
     Selection never consumes or edits source photos.

  03 CreateImage
     Input: selected references, actual product and writing/scene rules.
     Output: one request with explicit image roles and a destination PNG path.
     ReferenceArchive copies every selected input (subject, scene, product, style)
     into refs/<item>/ before generation. The generator uses
     those copies. manifest.json records order, roles, source links and SHA256.
     Invoke-ImageGeneration executes that request. The final result is one
     continuous scene. Additional references never become a collage.

  04 CompleteImage
     Deliver the first completed PNG, byte-for-byte as returned by the image tool.
     Only PNG readability is checked in code. The user reviews the exported image.
     Retry up to 3 submissions only on connection/timeout failures without output;
     recover an already saved image before submitting another request.

  05 WriteReview
     Input: delivered image and actual product context.
     Output: short English demo review, focused on visible product details.
     Editorial rules use ordinary language and varied rhythm while preserving
     factual limits. No separate rewrite call is made.
     Random metadata is still blank at this point.

After each successful item
  Step 07 checkpoints its image/review row into CSV, then updates URL history and
  removes that URL from the pending queue. Failed URLs remain queued.
  Storage failures stop the batch instead of silently consuming more input.

After ALL workers finish
  Step 06 fills author, rating, @int email and current-year UTC date locally.
  verified_purchase stays true. No Codex call is used for these fields.
  Step 07 writes the final CSV, including successes from a partially failed batch.
  The batch returns an error status if any URL remains failed.
  An interrupted batch may have checkpoint rows with blank random metadata.

Boundaries
  workflow/       Defines execution order and failure boundaries.
  workflow/steps/ Implements each numbered operation.
  application/    Resolves application configuration and creates batch folders.
  domain/         Loads product and editorial rules without running AI work.
  infrastructure/ Owns IO: Codex, sample catalog, URL queue, CSV, atomic file writes.
  ui/             Displays progress and launches the public CLI entry point.
                  Detailed logs stay in batch logs; users see main milestones.

Data ownership
  data/source-photos/ catalog.json and categorized reusable photos (read-only).
  data/names.txt      Reusable author sample pool.
  data/*.json         Product contexts and editorial rules.
  data/image-style/   Camera/framing example only.
  data/review-samples.jsonl Extracted review text, rating and source for the
                      101 reviews summarized in review-style.json. Not read at runtime.
  workspace/output/<batch>/     Everything from one run: images/, refs/, logs/, loox_import.csv.
  workspace/output/<batch>/urls.input.txt Input URLs for this run.
  workspace/output/<batch>/urls.completed.txt Successful URL checkpoints for this run.
  The GUI copies its run log into <batch>/logs/run.log when the run ends.
  workspace.ps1 centralizes runtime paths.
  CLI -List/-OutDir overrides remain supported for explicit custom destinations.

Failure handling
  Primary categories outrank fallbacks.
  An optional second scene may be omitted only when a checked real reference already
  supplies a compatible setting. Zero valid references still stops the product.
  Product page/image downloads allow 30 seconds per request and retry transient
  network/server errors up to 3 attempts. Password gates and permanent errors stop
  immediately. The GUI distinguishes timeouts, inaccessible links and missing pages.
  Codex transport retries transient capacity/rate-limit errors up to 3 attempts
  without changing models. Authentication and credit errors stop immediately.
  Image quality repair is separate and limited to one replacement image.
  Queue locking prevents two processes from consuming the same queue at once.

Maintenance
  Edit product categories/settings in data/product-contexts.json.
  Edit review rhythm profiles in data/review-style.json and editorial constraints
  in data/writing-style.json. Keep source provenance with derived data.
  Add new executable modules to src/bootstrap.ps1 so workers load them too.
  Keep orchestration in ProductWorkflow/BatchWorkflow, IO in infrastructure.
  Run test.cmd before distributing changes. The tests call no paid AI services.
  Review-pipeline checks parallel work, partial failures, successful retries,
  empty queues, CSV fields, source preservation and metadata timing.
